## 一、项目概述

基于 Django 的在线考试系统，覆盖「出题 → 组卷 → 考试 → 判分 → 学情 → 推荐 → 作弊检测 → 班级/用户治理」完整闭环，AI 能力通过第三方大模型接入（DeepSeek / 豆包 / 元宝 / OpenAI 兼容端点）。

| 项 | 值 |
|---|---|
| 后端 | Django 4.2 LTS + DRF 3.16 + SimpleJWT + drf-spectacular |
| 数据库 | MySQL 5.6.46（兼容 8.0，见部署文档） |
| 前端 | Django 模板 + Bootstrap 5 + 原生 fetch（无构建步骤） |
| 代码规模 | 54,408 行（Python + 模板 + JS + CSS，**不含空行**，含测试与迁移） |
| 数据模型 | **15 张业务表**，11 个 app |
| 对外接口 | `/api/v1/` 下 **124 个「路径×方法」操作**（不含 DRF 根路由） |
| 页面 | 31 个模板，学生 / 教师 / 管理员三角色分流 |

## 三、值得说明的设计决策

这些不是"实现了功能"，而是踩过坑之后定下来的约束，都有测试守着：

**1. 答案防泄漏靠序列化器分层，不靠前端隐藏**
学生视角的序列化器里**根本没有** `reference_answer` / `analysis` / `options[].is_correct` 这些字段，而不是传给前端再隐藏。考试下发只有一个出口（`_question_payload()`），回归测试断言 payload 字符串不含敏感字段。

**2. 服务端是唯一计时权威**
`deadline_at` 在开考那刻算好落库（并被考试结束时间封顶），前端倒计时只做展示。心跳上报的客户端剩余时间**只当观测值，绝不参与判据**。交卷留 30 秒宽限期，网络抖动不至于被判超时。

**3. 确定性乱序：同一份卷子刷新不换题**
`shuffle_seed` 落在 attempt 上，选项乱序把题号掺进种子。学生刷新页面、换设备、断网重连看到的题序完全一致——这不是体验问题，是公平性问题。

**4. AI 一律降级，不抛异常**
模型不可用 / 返回非 JSON / 字段缺失 → 本地规则兜底 + `degraded=True`，学生端永远能看到一份能看的诊断。大模型输出当**不可信输入**处理：能修就修，修不了丢进 `errors`，绝不让一条脏数据打断整批。

**5. 算法定正确性，AI 只负责可解释性**
智能组卷由纯算法抽题，可验证、可复现（支持 `seed`）；AI 只写「组卷说明」。**绝不让模型直接输出题目 id**——否则同一份需求每次生成不同的卷子，无法审计。

**6. 汇总只有一个写入口，靠"重算"保证幂等**
成绩总分每次从 `Answer` 重算，而不是 `score += x`。判分、复核、出分三条路径都走同一个 `recalc()`，杜绝重复累加。同理，试卷的总分/题数冗余字段也只由一个 `recalc()` 维护。

**7. 统计是只读模型，不建表**
学情统计、推荐清单都不落库：数字从已判分的作答现算；推荐是 `md5(student|date|question)` 打散后的**确定性函数**——同一学生同一天刷新不换题、跨天自然轮换。只有 AI 诊断文本需要缓存，用 `update_or_create` 覆盖不堆积。

**8. 埋点只存事实，结论读时现算**
切屏几次是客观事实；「算不算可疑」依赖可配阈值，所以结论一律读时计算。教师改阈值后历史结论不会过时，也不用回填旧数据。

**9. 软约束要"跳过 + 回报"，不要整批拒绝**
批量加人 / 批量导入时，冲突项跳过并在明细里说明原因（带行号），而不是一个冲突就拖垮整批。同时**判定不了就不拦**——缺老师/学科/年级时放行，宁可漏拦也不误伤。

**10. 业务同义字段一律先归一化再比**
年级会写成 `2026` / `2026级` / `2026届`，题干会有全角括号和多余空格。凡是靠字符串相等判断"是不是同一个"的地方，都先归一化（年级取 4 位年份、题干走 NFKC + 去空白）。改数据只能治一时，代码归一化才治本。

**11. 「面向全体」的范围由创建者决定，不是一个布尔值说了算**
`open_to_all=true` 看起来像"全校"，但教师建一场"全体考试"，指的应该是**他自己的学生**，而不是全校所有人。所以范围由 `Exam.open_to_all_scope()` 按创建者算：教师 → 自己可管理班级里的学生，管理员/无主 → 全校。这条同时作用于学生端列表、开考校验和应考人数——三处必须用同一个范围，否则会出现"列表里看得到、点进去开不了考"的割裂。也刻意没按 `subject` 二次过滤：学科已隐含在班级关系里，再按考试学科比一次，反而会因写法不一致漏掉该覆盖的学生。

## 七、已知局限

如实列出，均不阻塞交付：

1. **性能数据来自开发服务器**：Django dev server 单进程，20 用户下响应时间从 135ms 劣化到 2.4s（约 18 倍）。生产需在 gunicorn + 多 worker 下重跑才有参考价值。
2. **两个未优化的热点**：`POST /exams/{id}/start/`（20 用户 3.3s）与 `GET /grading/queue/`（619ms）。
3. **题库判重是内存比对**：库内候选按学科整批拉回内存归一化比较，单学科万级题量时有一次性开销；彻底优化需加 `stem_hash` 冗余列（需迁移）。
4. **越权页是裸 403**：Django 默认纯文本，无导航与返回入口，缺 `templates/403.html`。
5. **MySQL 5.6 已停止维护**：升 8.0 后可删除 `DB_CHARSET` / `DB_SKIP_VERSION_CHECK` 兼容配置，并改用 `utf8mb4`。
6. **AI 批改未做压测**：性能测试刻意绕过真实大模型（成本与可复现性），AI 场景的响应时间未纳入指标。
7. **学号派发无数据库唯一约束**：`student_no` 允许为空，MySQL 5.6 又不支持条件唯一索引，
   所以派发靠「取最大值 +1 后再查重」而非 DB 约束。极端并发（同一毫秒多人注册）仍可能撞号，
   真要做强一致需升级 MySQL 8.0 并加「非空时唯一」的函数索引。
