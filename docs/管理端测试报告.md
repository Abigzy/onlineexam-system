## 0. 结论摘要（给主理人）

1. **权限红线全部守住**：非管理员进 `/manage/*` 一律 302 且响应体为空（无内容泄露）；学生进教师业务页仍是 **403**（没有被 mixin 改成 302）；学生进 `/classrooms/` 仍是 **200**。这三条是本次改造最容易踩雷的地方，均通过。
2. **账号治理可用**：随机密码能过 `AUTH_PASSWORD_VALIDATORS`、明文只出现在 `data.password` 一次、弱密码全部被拒、旧密码立即失效、停用即时踢 Session 并让旧 JWT 401、最后一个启用管理员无法被停用/降级（服务层 + 接口层 + 页面层三处都有拦截）。
3. **零迁移、零既有测试改动**：`makemigrations --check` → `No changes detected`；`apps/system/` 无 migrations 目录；既有 781 条测试文件 mtime 全部早于本批次，数量守恒（781 + 110 + 67 = 958）。
4. **一项源码缺陷（P2）已在 Round 2 修复并复验**：`apps/users/serializers.py:14` 原从 `rest_framework_simplejwt.exceptions` 导入 `AuthenticationFailed`（是 DRF 版的**子类**），而 SimpleJWT 5.5.1 在 `TokenObtainSerializer.validate()` 里抛的是 **DRF 基类**实例 → `except AuthenticationFailed` 永不命中，接口登录失败返回 SimpleJWT 原始文案「找不到指定凭据对应的有效用户」，且 `if not self.user.is_active` 成为死代码。工程师按 A+B 修复（改 import + 在 `validate()` 里补 JWT 侧二次判定），QA 复验：**停用+密码正确 → 40101/「该账号已被停用」；其余三态 → 40100/「账号或密码错误」同码同文案（无枚举泄露）**。详见 §7-1。
5. **路由判定：无阻断项，可交付**。§7-1 / §7-2 均已在 Round 2 闭环；剩余为 3 条 P3 登记项与 2 条需人工验收的性能/响应式检查（AC-35/36）。

- 正常流程（`create_superuser` 默认 `role=admin`，见 `apps/users/managers.py:46-51`）不会触发；当前库内超管均为 `role=admin`，**现有数字不受影响**。
- 与工程师确认后的一致结论：`by_role` 定位为**并列维度**（不是对 `total` 的划分），页面也没有做「三桶加总 = 总数」的展示。
- **处理结果（Round 3）**：按共识**只加注释不改逻辑**——`SystemOverviewServices._user_metrics` 的 docstring 已写明「并列维度、可能重叠、不可相加」。QA 复核：统计数字未变（`DashboardNumberAccuracyTest` 仍全绿），口径已文档化。**本条闭环。**

### 7-4 【P3 · 已修复】随机密码兜底为固定常量

- 原状：`apps/users/services.py` 的 `FALLBACK_RESET_PASSWORD = "Exam@2026"`，连续 5 次随机值未过校验时落到该常量（概率极低，但有「固定后门值」的理论风险）。

### 7-5 【P3 · 说明】`toggle-active` 的「最后管理员」护栏在接口层近乎不可达

- 操作者自身必然是「启用的管理员」，所以对**别人**停用时 `remaining ≥ 1` 恒成立；对**自己**停用会先被 `views.py:278-279` 的「不能停用自己」拦住。
- 因此 AC-18 的真实保护链是：**不能停用自己**（接口）+ **不能降级最后一个管理员**（服务层，可达，已自动化）+ 页面按钮置灰（`last_admin_id`）。
- 结论：语义成立，但 `views.py:281` 那行 `assert_admin_survives` 在停用路径上是防御性冗余——建议加注释说明，避免后人误以为它承担主要保护职责。
