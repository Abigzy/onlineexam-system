### 模块 7 · 个性化推荐 ✅

**7A · 应用与服务 `apps/recommend/`（不建新表）**
- [x] **推荐清单不落库**：它是「同一学生 + 同一天 → 同一份清单」的**确定性函数**，
      刷新页面不会换题，所以不需要一张表去缓存它（与模块六「学情统计不建表」同源）
- [x] 三个服务：`ContentBasedService`（内容分）/ `CollaborativeFilteringService`
      （item-based 协同过滤）/ `RecommendationService`（成集 + 推荐理由 + AI 改写）
- [x] **只读两样东西**：模块五的判分结果、模块六的 `student_mastery()`。
      薄弱点直接取 `weak_points`，**绝不在这里重算掌握度**

**7B · 内容推荐 `ContentBasedService`**
- [x] 内容分 = `薄弱度 × 0.65 + 难度适配度 × 0.35`
- [x] 薄弱度 = `(1 - 正确率) × 证据充分度`——正确率 0% 是饱和的（做过 12 题全错和
      做过 2 题全错都是 0%），折进证据充分度（`EVIDENCE_FULL_SAMPLE=8`）才排得出先后
- [x] 难度目标 `target = 1 + round(正确率 × 3)`，夹在 1..4；**难度不是越高越好**，
      而是越接近「略高于当前水平」越好（提示词里写着「避免过难打击信心」）
- [x] 候选池 = 薄弱知识点**及其全部后代**上的题（父知识点薄弱 → 挂在子知识点上的题

- [x] **已做对的题不再推荐**（那是「已掌握」不是「要练」）；做错过的题留在池子里，
      并在卡片上标「做错过」

**7C · 协同过滤 `CollaborativeFilteringService`**
- [x] 学生 × 题目 0/1 矩阵（客观题看 `is_correct`、主观题看得分率 ≥60%，与学情同口径）

- [x] 得分 = 候选题目与「该生做错过的每一道题」相似度的均值，归一化到 0~1

- [x] 以**乘数**形式参与（`match = 内容分 × (1 + 30% × 协同分)`），而不是加权平均——

> 但单题 `/save/` 仍是老行为——返 400，状态停在 `in_progress`，要等心跳才结算。

- [x] **根因是外层又套了一层事务**：`save_answer()` 自己带 `@transaction.atomic`，
      它调 `save_answers()`（内部已拆成「先收卷、再拒绝」两个事务）时，抛出的 400
      把**外层**事务整个回滚，连刚提交的收卷也一起撤了。批量视图直接调
      `save_answers()`、没有外层事务，所以修复只在批量路径生效
- [x] 修法：去掉 `save_answer()` 的 `@transaction.atomic`——它内部只有一次读
      （回显这道题的最新态），不需要事务；事务边界交给 `save_answers()` 自己管
- [x] **影响面**：一屏一题模式下每题切走都会打 `/save/`。超时后学生继续操作，
      作答一直卡在 `in_progress`，教师侧显示「进行中」、`finalize` 被拒
- [x] 补测试 2 条：`test_overdue_single_save_also_submits`（单题入口同样必须先收卷）
      + `test_single_save_works_normally`（去注解不能把正常暂存弄坏）
- [x] **有效性验证**：把注解加回去 → 单题用例报 `'in_progress' == 'in_progress'`
- [x] 真机（超时 30 分钟后调 `/save/`）：HTTP 400 / `本次作答已结束`，
      **状态 = `timeout`、`is_finished = True`**
- [x] **顺手扫了一遍同类模式**（AST：`@transaction.atomic` + 写库 + 抛业务异常，17 处）：
      `resolve_expiry` 只有 3 个调用点——`save_answers` / `save_answer`（本次修完）、
      `heartbeat` 与 `get_state`（**都不抛异常**，不会回滚）。
      其余 15 处都是「校验失败整体回滚」，属正确语义；
      `start` 里被回滚的 `sync_status` 是幂等推导，下次请求会重做，无状态矛盾
- [x] 验收：`apps.exam` 全绿；全量 **1184 passed**（2 skipped）

**11J · BUG-02（UI 自动化阶段）：题目编辑器提交空选项行，400 且提示 `[object Object]`**

> 来源：配套 UI 自动化测试项目《缺陷管理》 BUG-02。
> 新增页默认渲染 A/B/C/D 四个空选项行，用户只填两行是**最常见操作**，
> 结果保存失败，toast 显示 `options：[object Object]；[object Object]；…`。

- [x] **根因是两处叠加，缺一不可**：
      1. `templates/questions/editor.html::collect()` 把四个 `.option-row` 全塞进 payload，
         **没过滤空行**；而 `validate()` 只统计「有内容的」，所以校验通过了——口径不一致
      2. 后端 `QuestionOptionInputSerializer.content` 是 `allow_blank=False`，四个空行
         各返回一个错误对象；DRF 错误是嵌套结构，`UI.errorText()` 对数组直接 `String(item)`
         → 全变 `[object Object]`
- [x] **修法（1 + 2 都做，后端不放宽）**：
      ① `collect()` 末尾加 `.filter(o => o.content)`，与 `validate()` 对齐；
      ② `UI.errorText()` 改成递归展平，**列表项标序号**、内层对象只取文案不重复字段名
- [x] **后端刻意不改** `allow_blank=False`：改成 True 会让空行静默入库，题库出现空白选项。
      补守门测试 `test_option_content_cannot_be_blank` 锁住这个口径
- [x] 实测（后端）：只提交 2 个选项 → `HTTP 201 / code=0`；带 2 个空行 → `HTTP 400`
      （确认该由前端过滤，而不是后端放宽）
- [x] 实测（错误渲染）：缺陷里的真实报文
      `{options: [{}, {}, {content:["该字段不能为空。"]}, {...}]}` 现在渲染成
      **`options：第 3 项：该字段不能为空。；第 4 项：该字段不能为空。`**
- [x] **为什么两层都要修**：只修①，其他接口的嵌套错误仍是 `[object Object]`；
      只修②，提示可读了但操作还是失败（用户仍要自己删空行）
- [x] **未做**「自动删除空行」的 DOM 操作：用户正填第 3 行时误点保存会丢输入，
      用「过滤（忽略）」比「删除」安全
- [x] 验收：`apps.questions` 71 条全绿；内联 JS 26 块 0 失败；`api.js` 语法检查通过

**11K · BUG-03（UI 自动化阶段，严重）：组卷页单个知识点勾选完全无效**

> 来源：配套 UI 自动化测试项目《缺陷管理》 BUG-03。
> 勾选单个知识点后题池毫无变化、预览请求 `knowledge_point_ids: []`，
> 但复选框显示已勾选——**静默失效**，教师以为按知识点组了卷，实际按整学科抽题。

- [x] **根因**：`templates/papers/compose.html` 的监听器第一行
      `if (!event.target.dataset.kp) return;`。DOM 是**无值属性** `data-kp`，
      所以 `dataset.kp === ""`，空字符串 falsy → **恒 return**。
      一句话：把「属性存在性判断」写成了「属性值真值判断」
- [x] 修法：改用 `if (!event.target.hasAttribute("data-kp")) return;`。
      **没动模板**（`data-kp` 保持无值属性）——属性选择器 `input[data-kp]` 不受影响
- [x] 顺带（缺陷单的建议②）：题池为空时按是否选了知识点给不同文案——
      选了 N 个 → 「所选 N 个知识点下没有可用题目，可以少选几个或换学科试试」；
      没选 → 原「当前条件下题库里没有可用题目」
- [x] **接口侧复核**（确认后端无需改）：`/papers/pool/?knowledge_point_ids=X` 本来就能收敛，
      admin 视角不筛选 2429 → 单知识点 83 / 95 / 63。问题纯在前端没把勾选送出去
- [x] **新增 `apps/system/tests/test_frontend_guards.py`（7 条静态守卫）**：
      BUG-03 两条（必须用 `hasAttribute` + 不许退回真值判断）+ 全选仍用属性选择器；
      BUG-02 三条（`collect()` 过滤空选项、校验与提交同口径、后端不放宽 `allow_blank`）
- [x] **有效性验证**：把监听器改回 `!event.target.dataset.kp` → 2 条立即失败
- [x] **为什么用静态断言而不是 E2E**：这类缺陷的故障模式是「页面正常、功能没生效」——
      接口测试看不到（请求根本没发出去），人工点一遍也容易以为"题池本来就这么多"。
      1ms 的静态守卫能在提交前拦住回退，比等 E2E 回归快
- [x] 验收：`apps.system` 全绿；内联 JS 26 块 0 失败
- [x] 验收：全量 **1197 passed**（2 skipped）；`apps.system` 全绿；`api.js` 语法 OK
